# 00 · 怎么读这个项目

> 别从第一个文件往后读。按「问题」跳，读完一类问题再跳下一类。

---

## 路线 A：先搞清楚「一次选课发生了什么」（推荐，40 分钟）

按这个顺序读，每个文件只看指定部分：

| 步骤 | 打开 | 只看什么 |
|---|---|---|
| 1 | `cs-enroll/controller/EnrollController.java` | `enroll()` 方法：路径、header、参数 |
| 2 | `cs-enroll/service/EnrollService.java` | `enroll()` 方法：①幂等 → ②取信息 → ③校验 → ④Try → ⑤落单 → ⑥Confirm |
| 3 | `cs-enroll/service/EnrollService.java` | `checkRules()`：四条规则 |
| 4 | `cs-course/service/CapacityService.java` | `reserve()`：条件更新扣容量 + 插预占记录 |
| 5 | `cs-course/service/CapacityService.java` | `confirm()`：CAS 0→1；`cancel()`：CAS 0→2 + 回补 |
| 6 | `cs-course/mapper/CourseClassMapper.java` | `deduct`：一条 UPDATE 完成判断和扣减 |

**读完自测**：不看代码，说出「第 4 步和第 6 步之间，如果课程服务超时了会发生什么」。

## 路线 B：先搞清楚「失败会怎样」（30 分钟，面试最爱问）

| 失败点 | 打开 | 机制 |
|---|---|---|
| 用户连点两次 | `EnrollService.enroll` ① | Redis `SETNX idem:enroll:{token}`，5 分钟 |
| Try 成功、本地落单失败 | `EnrollService.enroll` ⑤ catch | `safeCancel(reserveId)` 回滚 |
| 本地成功、Confirm 失败 | `EnrollService.enroll` ⑥ catch | 本地改回 + Cancel，两边都当没选 |
| Confirm 请求重复到达 | `CapacityService.confirm` | CAS 0→1 只成功一次，第二次读到 1 直接返回 |
| Cancel 先到、Try 后到（悬挂） | `CapacityService.cancel` | 落「墓碑」记录 status=2 |
| Try 根本没到就收到 Cancel（空回滚） | `CapacityService.cancel` | 同上，墓碑挡住后续 Try |
| 服务崩了、预占没人确认 | `CapacityService.scheduledRelease` | 每 30 秒扫 `status=0 AND expire_time<now()` |
| 退课时远程失败 | `EnrollService.drop` + `OutboxRelay` | 本地落 Outbox，中继指数退避重试，5 次转死信 |

## 路线 C：先搞清楚「为什么这么拆」（30 分钟，架构视角）

1. `docs/01-架构与拆分.md`：边界、数据归属、一致性方案选型
2. `cs-enroll/service/EnrollService.java` 顶部注释：为什么用 `TransactionTemplate` 而不是 `@Transactional`
3. `cs-gateway/filter/AuthGlobalFilter.java`：为什么鉴权上提到网关
4. `cs-enroll/service/OutboxRelay.java`：为什么消息要先进库再投递

---

## 读代码时的三个约定

| 你会看到 | 含义 |
|---|---|
| `status` 0/1/2/3 | 预占记录的四态：预占中 / 已确认 / 已取消 / 超时释放 |
| `casStatus(id, from, to)` | 带原状态的更新，影响行数 0 说明状态已变 |
| `unwrap(result, action)` | 统一处理 Feign 返回：`code != 0` 就抛业务异常 |

## 一天读不完就分三天

- 第 1 天：路线 A（主线跑通）
- 第 2 天：路线 B（失败路径，把上面 8 条各讲一遍录音）
- 第 3 天：路线 C + 自己动手改一处（比如把 TTL 改成 30 秒，观察对账释放）
