# 02 · 核心链路时序

## 一、选课（成功路径）

```
客户端        gateway        enroll-service              course-service
  │              │                  │                          │
  │ POST /api/enrollments           │                          │
  │ X-Idempotent-Token: uuid        │                          │
  │─────────────▶│                  │                          │
  │              │ 查 Redis token   │                          │
  │              │ → studentId      │                          │
  │              │ 加 X-Student-Id  │                          │
  │              │─────────────────▶│                          │
  │              │                  │ ① SETNX idem:{token}     │
  │              │                  │    失败 → 3001 拒绝       │
  │              │                  │                          │
  │              │                  │ ② GET /internal/classes/{id}
  │              │                  │─────────────────────────▶│
  │              │                  │◀── 课程+学分+先修+排课 ───│
  │              │                  │                          │
  │              │                  │ ③ 四条规则（本地库）      │
  │              │                  │    重复/学分/先修/冲突    │
  │              │                  │                          │
  │              │                  │ ④ POST /capacity/reserve │
  │              │                  │─────────────────────────▶│
  │              │                  │                          │ UPDATE t_class
  │              │                  │                          │  SET remain=remain-1
  │              │                  │                          │  WHERE id=? AND remain>0
  │              │                  │                          │ INSERT t_capacity_reserve
  │              │                  │                          │  status=0, expire=+120s
  │              │                  │◀──── reserveId, remain ──│
  │              │                  │                          │
  │              │                  │ ⑤ 本地事务：              │
  │              │                  │    INSERT t_enrollment   │
  │              │                  │    INSERT t_outbox       │
  │              │                  │                          │
  │              │                  │ ⑥ POST /capacity/{id}/confirm
  │              │                  │─────────────────────────▶│
  │              │                  │                          │ CAS 0→1
  │              │                  │◀──────── ok ─────────────│
  │◀── 200 enrollNo ───────────────│                          │
```

**每一步为什么在这个位置**：

| 步 | 为什么不能挪 |
|---|---|
| ① 幂等在远程调用之前 | 拦住重复请求，省掉后面所有开销 |
| ③ 规则校验在 Try 之前 | 先筛掉明显不合格的，不要白占容量 |
| ④ Try 在落单之前 | 没容量就不要写单，避免脏数据 |
| ⑤ 落单在 Confirm 之前 | 先有单再确认；反过来会出现「容量确认了但单没写」 |
| ⑥ Confirm 最后 | 它是「正式生效」的那一下 |

## 二、失败路径（这才是面试要问的）

| 位置 | 失败现象 | 处理 | 谁兜底 |
|---|---|---|---|
| ① | 同一个 token 再进来 | 返回 3001，不重新执行 | Redis TTL 5 分钟 |
| ② | course 超时 | 抛 2000「课程服务不可用」 | 用户重试 |
| ③ | 规则不满足 | 直接返回 3001/3002/3003/3004 | 无副作用 |
| ④ | 容量为 0 | SQL 影响行数 0 → 2003 | 无副作用 |
| ④ | course 超时但实际成功了 | enroll 抛异常，用户重试时会用**新的 reserveId** | 旧预占无人确认 → **对账释放** |
| ⑤ | 本地落单失败 | `safeCancel(reserveId)` 回滚容量 | 远程 Cancel；再失败靠对账 |
| ⑥ | Confirm 超时/失败 | 本地改回 status=0 + Cancel | 对账 |
| ⑥ | Confirm 重复到达 | CAS 影响行数 0 → 读到已是 1 → 幂等返回 | 状态机 |

**④ 那一行最值得讲**：远程超时的时候，你根本不知道对方成没成功。所以设计上必须允许「最坏情况留一条没人确认的预占」，靠对账去清。**这不是漏洞，是分布式系统的常态——本地无法确定远程的结果时，必须有一个补偿通道。**

## 三、退课（业务动作，不是补偿）

```
客户端 ──▶ enroll: 本地事务（status 1→0 + 落 Outbox ENROLL_CANCEL）
                    │
                    ├─ 立即尝试 POST /capacity/{id}/release
                    │     成功 → 把 Outbox 标记为已投递
                    │     失败 → 留给中继任务重试（2^n 秒退避，5 次转死信）
                    ▼
              course: release() —— CAS 1→2 并回补容量
```

**为什么先改本地再调远程**：

- 反过来的话，远程释放成功、本地更新失败 → 容量放了但选课单还在 → **可能超卖**
- 现在这个顺序，最坏情况是「单退了但容量没还」→ 只是浪费容量，不会错卖

**宁可少卖，不可超卖。** 这是所有交易系统的第一原则。

## 四、超时释放（对账）

```
cs-course 内部：@Scheduled(fixedDelay = 30s)
  SELECT reserve_id FROM t_capacity_reserve
   WHERE status = 0 AND expire_time < NOW() LIMIT 200
  ↓ 对每一条
  CAS 0 → 3   （成功才回补，避免和 Confirm 抢）
  UPDATE t_class SET remain = remain + 1 WHERE id = ? AND remain < capacity
```

**为什么要 CAS**：扫描到的那一刻，上游可能刚好把 Confirm 发过来了。CAS 保证只有一方能改成功——**并发下永远用状态机做仲裁，不要用「先查后改」**。

另外 `cs-enroll` 还有一个 `POST /internal/reconcile` 可以主动触发，形成「本地定时 + 上游对账」双保险。

## 五、Outbox 中继

```
业务事务里：INSERT t_enrollment + INSERT t_outbox_message   ← 同一事务
                    ↓
@Scheduled(5s)：SELECT ... WHERE status=0 AND next_retry_time<=NOW()
                    ↓
           投递（这里：调用 course 的 release，或发通知）
                    ↓
           成功 → status=1；失败 → retry_count+1，next_retry_time = now + 2^n 秒
                    ↓
           retry_count >= 5 → status=2（死信，人工介入）
```

**核心问题**：「消息发出去了，但业务事务回滚了」或者「业务提交了，消息丢了」。

**Outbox 的答案**：把消息当成业务数据的一部分，和业务**同一个事务**写库。只要事务提交，消息就一定在库里；剩下的只是「什么时候发出去」，而这件事可以重试。

**一个必须讲的细节**：中继消费要**幂等**——投递成功但标记状态前崩溃，下次会重复投递。所以下游的 release/cancel 必须幂等（这个项目里是幂等的）。
