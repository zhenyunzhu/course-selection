# 01 · 架构与拆分

## 一、为什么是三个服务，不是五个

```
cs-gateway ──▶ cs-enroll ──Feign──▶ cs-course
```

拆分依据是**数据归属**，不是「技术分层」：

| 服务 | 拥有什么数据 | 为什么单独拆 |
|---|---|---|
| `cs-course` | 课程、教学班、容量、排课时间 | 容量是热点资源，需要独立扩缩容和独立的库 |
| `cs-enroll` | 选课单、学分、Outbox | 规则校验要读选课表，和课程是两个变化频率 |
| `cs-gateway` | 无 | 统一鉴权入口，避免每个服务各写一份 token 解析 |

**没有拆成 5 个的原因**：这个业务只有两个真正的限界上下文。「用户」「通知」「搜索」拆出去只会增加跨服务调用次数，换不来任何好处——**微服务的成本是分布式复杂度，必须换到实打实的收益才值得**。

---

## 二、数据归属：一个库一个服务

| 库 | 归属 | 表 |
|---|---|---|
| `cs_course` | cs-course | `t_course`、`t_class`、`t_class_schedule`、`t_capacity_reserve` |
| `cs_enroll` | cs-enroll | `t_enrollment`、`t_outbox_message` |

**没有任何一张表被两个服务直接读写。** 跨服务只能走接口，这是边界是否真实的唯一检验标准。

一个容易问的点：`t_enrollment` 里为什么存了 `course_name`、`credit`、`schedule_snapshot`？

> 那是**快照**。规则校验（学分、时间冲突）如果每次去 course 查，一个学生选 10 门课就是 10 次远程调用。存快照后，校验全部本地完成，只有「选课」这一条链路需要远程。

## 三、核心矛盾：跨服务一致性

### 问题

原来单体里，扣容量和写选课单在同一个 `@Transactional` 里。拆开以后：

- 容量在 `cs-course` 的库
- 选课单在 `cs-enroll` 的库
- **本地事务管不到另一个库**

### 四个候选方案与取舍

| 方案 | 做法 | 为什么不用 / 用 |
|---|---|---|
| 把容量挪到 enroll | 合并回单体 | 那就不用拆了，边界被破坏 |
| 2PC / Seata AT | 全局锁 + undo log 自动回滚 | 全局锁在抢课热点上会放大冲突；而且「锁住别人的库」这件事在跨团队时很难谈 |
| **纯消息最终一致** | 先写单，再发消息扣容量 | 选课要求**实时反馈**：学生点完就要知道选上没有，中间态不可接受 |
| **TCC 变体：预占-确认-取消** ✅ | 先占住容量，本地落单成功再确认 | 窗口期只有几十毫秒，且失败可补偿 |

**选它的核心理由**：容量是「先占后用」的资源，天然适合预占。而且预占记录本身就是一份可对账的凭据——出事能查。

## 四、状态机（整个项目的骨架）

`t_capacity_reserve.status`：

```
         reserve()                confirm()
   ─────────────────▶ 0 预占中 ──────────────▶ 1 已确认
                        │  │
              cancel()  │  │  expire_time 到（对账扫描）
                        ▼  ▼
                   2 已取消   3 超时释放
                        ▲
        release()（退课）│
                        └──────── 1 已确认
```

四条规则，写在 `CapacityService` 里：

1. **只有 0 能流转到 1 或 2**（CAS 保证），所以重复 Confirm、重复 Cancel 都不会改坏数据
2. **1 只能通过 release 回到 2**（退课是业务动作，不是补偿）
3. **2 和 3 是终态**，再来的请求一律幂等返回
4. 每次从 `0 → 2/3` 都要**回补容量**，且回补语句带 `remain < capacity` 兜底，防止加多

## 五、鉴权为什么放在网关

`AuthGlobalFilter` 做三件事：取 `Authorization` → 查 Redis 拿 studentId → 把 `X-Student-Id` 塞进请求头。

| 放业务服务里 | 放网关 |
|---|---|
| 每个服务都要解析 token | 只有一份实现 |
| 换鉴权方案要改 N 个服务 | 只改网关 |
| 下游可能忘记校验 | 网关统一拦，下游默认信任 |

**下游为什么敢信任 `X-Student-Id`？** 因为 `/internal/**` 和网关路由是隔离的：网关只路由 `/api/**`，外部进不来。生产还要在网络层把服务端口限制在集群内。

## 六、这个架构的三个已知弱点（面试可以主动说）

1. **容量热点**：`UPDATE t_class SET remain=remain-1` 在单个教学班上仍是行锁串行。上量要改成 Redis 预扣 + 异步落库（就是 venue-booking 那套）
2. **对账是轮询**：30 秒一次，最坏情况容量被占 30 秒。生产应该用延迟消息精确到点
3. **没有服务治理**：没有限流、熔断、链路追踪。生产要加 Sentinel + Micrometer Tracing

**能主动说出弱点，比说「我的架构很完善」可信十倍。**
